# 文字加密恢复与历史归档（本地开发）

此阶段仅处理文字。图片、视频、文件保持原有传输与存储方式。

## 使用流程

1. 旧手机打开「文字加密」，先登记设备，再创建恢复码。恢复码需离线保存；它能批准同账号新设备并解密该账号的归档，不应发送给其他人。
2. 点击「归档本机已解密的历史」补齐既有历史。设置恢复码后，新解密的文字也会自动归档。网络中断时可重试；已完成的归档不会重复上传。
3. 新手机登录同一账号、登记设备，输入恢复码批准本机，然后点击「恢复已归档的历史」。新手机生成全新的签名密钥和 MLS 状态，不恢复旧发送棘轮。
4. 其他设备独立核对新手机公钥，原管理设备更新会话成员；新手机同步会话密钥后即可收发新消息。
5. 原管理设备丢失时先撤销它。仍持有该会话 MLS 状态的授权成员可接管；管理员在已解锁设备上也可通过「恢复失去管理设备的会话」接管，要求当前 IM_READ 和 ACCESS_MANAGE 权限并核对设备公钥。

若本机数据库仍在但系统 Keychain 密钥已丢失，页面会提供「重新建立本机加密设备」：保留旧密文文件，生成新的设备与数据库，再按恢复流程操作。此入口不会覆盖仍存在的私钥。

管理员恢复码与用户恢复码按账号、用途隔离。管理员仍需在本机解锁保险库，且每次归档、恢复和读取均检查当前权限并记录访问原因；服务器不持有恢复秘密或设备私钥。

## 数据与保留规则

- 恢复码为设备 CSPRNG 生成的 256 位随机秘密，含输入校验码。HKDF-SHA256 按账号、用途分离归档 AES-256-GCM 密钥与 Ed25519 恢复签名密钥。
- 服务端仅保存恢复公钥、设备公钥和逐条加密归档。批准新设备需要登录凭证、新设备签名、恢复签名三者一致；已撤销设备不能重新批准。
- 本机将历史与重试数据从热会话状态分离，使用 SQLite / IndexedDB 的独立加密记录与索引分页。密钥推进与对应记录仍在同一事务提交，超过 1000 条不会触发旧容量上限。
- 服务端归档关联原消息。读取、恢复和上传检查成员状态、本人及会话清空水位、撤回、焚毁期限；撤回/删除、清空/退群、注销账号的数据库操作会清除相应归档。到期记录即使后台清理尚未执行也不能读取，后续扫描会删除。
- 本地缓存文字每次显示前重新检查服务端可见性，因此当前版本需要在线读取。用户已经抄录、截图或另存的内容无法由撤销操作追回。
- 归档按页处理、上传限制为每批最多两条大密文，避免超过默认 HTTP 请求体限制。重试会跳过已归档条目。

## 恢复边界

只能恢复曾经归档且仍符合保留规则的内容。未解密、未归档就丢失的旧记录无法从服务器明文重建。新设备不会自动信任服务器提供的设备公钥。

恢复后继续使用原会话，需要至少一台仍持有当前会话 MLS 状态的授权成员或管理员设备完成重新加入。所有会话状态都丢失时，恢复码仍能读取已归档历史，但不能回滚旧发送密钥继续发送。恢复码丢失且所有授权设备也丢失时，服务器没有可用来解密的后门。

## 本地验证

- 后端：`npx ts-node -r tsconfig-paths/register scripts/test-e2ee-local.ts`。真实本地 PostgreSQL、Nest HTTP、业务鉴权和 ChatService，临时数据完成后清理。
- App 安全存储：`node --test test/e2ee-native-journal.test.js`。
- 协议、恢复码与浏览器保险库：`npm test --prefix tools/e2ee-poc`；无 WebCrypto 路径：`npm run test:portable --prefix tools/e2ee-poc`。
- 真机离线入口：`tools/e2ee-device-acceptance/index.tsx`。通过 USB 内嵌包运行，所有数据在手机临时生成，无 HTTP、JWT 或真实用户数据。报告写到应用 Documents/e2ee-device-result.json，再通过 USB 取回。

真机离线检查与后端本机集成检查是两种独立证据；不能把它们表述为真实账号通过手机网络完成了全流程验收。
